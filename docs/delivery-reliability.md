# Native delivery contract (Phase 1)

## Previous state machine — inspected before implementation

AssettoServer callback -> payload/domain event ID -> new envelope GUID in bounded
memory channel -> dequeue -> increment pending counter -> serialize -> remember
frame -> send -> ACK receive removes pending entry regardless of accepted/error.
Send failure removes the pending entry without restoring the dequeued event.
Reconnect replays remembered frames and sends register/ready before starting the
ACK reader. Restart loses both memory channel and pending frames.

Envelope protocol is V1: protocolVersion, messageId, messageType, instanceId,
occurredAt, sentAt, delivery, payload, optional sequence. ACK has messageId,
instanceId, accepted, duplicate, error { code, message, retryable }. The Supervisor
persists synchronously into its game outbox before positive ACK, and deduplicates
by instance + envelope message ID. Existing IDs survived remembered-frame replay,
but not lost dequeues or plugin restart. Negative storage ACKs incorrectly omitted
retryable classification. Ephemeral snapshots never had durable acceptance.

## Implementation contract

Validated serialized envelope -> flushed atomic per-record local spool file ->
send eligible -> bounded in-flight window -> Supervisor outbox persistence ->
positive ACK -> local retirement. Send failure/timeout/reconnect retains the file
and its original message ID. Explicit permanent rejection retains a rejected file;
unknown ACK retains pending work. Record files avoid journal compaction and loading
payload history into RAM. Final operational details and measurements accompany the
Phase 1 report; no deployment is authorized.

## Storage and recovery

Atomic per-record files were selected instead of a journal or database: each
record can be recovered, rejected, quarantined, or retired independently without
rewriting all outstanding work. Only indexes/metadata stay resident; payloads
are read individually. Each formatVersion 1 wrapper includes the original V1
envelope and SHA-256 checksum. Checksums detect corruption, not hostile editing.

The default root is LocalApplicationData/Telematic/plugin-state, followed by
SHA-256 of the exact configured InstanceId and `spool`. The running account and
instance ID must remain stable. An optional Spool.RootDirectory must be absolute.
An exclusive owner.lock prevents two processes using the same instance spool.
Files validate their instance before replay. Windows newly created spool folders
use restricted inheritable permissions for the current user, SYSTEM, and admins;
reparse-point ancestors/files are refused. This is not an OS security boundary
between two processes running as the same user.

Defaults: Spool.MaxBytes=104857600 (100 MiB), Spool.MaxRecords=20000. Supported
limits are 1024 bytes through 1 GiB and 1 through 100000 records. Capacity counts
record contents including wrappers, rejected records, and quarantined files;
filesystem block/metadata overhead is additional. Individual outgoing envelopes
are limited to 120 KiB. No age-based competitive-event eviction occurs.

Capture serializes/validates before capacity/window accounting, writes a new
temporary file with WriteThrough and Flush(true), then renames in the same
directory. Linux additionally synchronizes the directory. Recovery promotes valid
complete temporary files and quarantines malformed/partial files; valid records
continue independently. A full or failed write refuses capture, emits a coded
error, and never sends an event as successfully persisted. Previously saved
records remain replayable. Existing spool data above a lowered configured cap is
retained, not truncated; further capture is refused.

Positive ACK cleanup deletes only the accepted record, freeing its content-byte
allowance. There is no journal compaction or whole-spool rewrite. Rejection
renames to a rejected filename containing a sanitized reason code; corruption
renames to quarantine. Neither is silently deleted. These exceptional cases
require investigation/export/removal by an operator, not routine SaaS upkeep.
Default directory creation, replay, and accepted-record cleanup are automatic.

## Message classification and ACK contract

Durable: instance.register, instance.ready, session.started, session.changed,
session.ended, driver.connected, driver.disconnected, lap.completed,
incident.car_collision, incident.environment_collision. session.ended is accepted
by the spool but not currently generated by the native bridge. No new native
lap correction, validity, or classification callbacks were invented.

Ephemeral outbound: connection.hello, instance.heartbeat, players.snapshot,
telemetry.snapshot, command.result. Inbound connection.accepted/rejected,
acknowledgement, and command.request are control messages, not spool events.
Players and telemetry use bounded/coalesced latest-state slots. Position/speed/
vehicle control samples are never persisted by this spool.

Envelope protocol remains 1. Hello advertises supportedDurableAckVersions=[2];
accepted must confirm durableAckVersion=2. New native Supervisor requires this
contract. Old native plugin/new Supervisor fails DURABLE_ACK_UPGRADE_REQUIRED;
new plugin/old Supervisor fails DURABLE_ACK_VERSION_UNSUPPORTED before replay.
Coordinate both binaries when an upgrade is separately authorized. Existing
non-native UDP adapters are not forced onto the native contract.

ACK payload reuses messageId, instanceId, accepted, duplicate, and
error {code,message,retryable}. Positive ACK requires an explicit true accepted
value, correct instance, known in-flight ID, and no error. Only this retires a
file. Duplicate positive ACK is harmless. Negative ACK must contain an explicit
retryable classification and code: true retains/retries, false preserves a
dead-letter record. Unknown, contradictory, malformed, foreign, or unsolicited
ACKs retain work. A send success alone never frees storage.

Supervisor validates durable events before ingest. Outbox full, storage I/O,
and rate limiting are retryable; invalid schemas/types/instance relationships
and oversized records are permanent. Positive ACK follows successful disk
outbox persistence, including deduplicated replay. This phase does not change
outbox-to-cloud upload/recovery behavior.

## Progress and status

Defaults: ConnectTimeoutSeconds=15 (connect plus application handshake),
WriteTimeoutSeconds=10, AckTimeoutSeconds=30, DurableRetrySeconds=2. The ACK
reader starts before bootstrap/replay, including when window/storage is full.
Oldest in-flight send exceeding its deadline cancels the connection. Replay
uses original file IDs with bounded 1-to-30-second exponential backoff plus up
to 250 ms jitter. Retryable negative ACKs pause durable retries without deleting
records. Stored files own all outstanding work across transport resets.

Diagnostics distinguish transport, spool health, observed Supervisor acceptance,
and cloud unknown. Plugin status includes pending/rejected/quarantined counts,
bytes/capacity, oldest timestamps, retry/accepted/capture-failure counts, durable
ACK/send/connection timestamps, and reconnects. Heartbeat metadata carries
delivery diagnostics; Supervisor connection status has receive/accept/rejection
counters. Counters are process-local, not permanent analytics. No per-position
log lines or credentials are added.

Synchronous durable capture adds disk latency to native callbacks. Flush/rename
recovery covers tested process failure points, not guaranteed hardware power
loss or damaged disks. Events before successful first persistence, manual spool
deletion, missing callbacks, changed service accounts/IDs, and exhausted storage
remain explicit loss boundaries. Supported runtime qualification requires fresh
net8 builds/tests plus an actual AssettoServer 0.0.54 loading check; supplemental
newer-runtime tests do not replace it.
